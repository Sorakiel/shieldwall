# MVP оболочки и журналов

Ветка: `feature/ui-log`, база: `main`.

## Объём

- Лимит цены для каждой армии и seed от 0 до 4294967295.
- Генерация двух армий через `ArmyGenerator`, показ состава, HP и стоимости.
- Команды «К бою», повторная генерация, изменение настроек и выход.
- Автобой через последовательные вызовы `BattleEngine::nextTurn()`.
- По два варианта фразы для всех семи `EventType`, отдельный текст про дальность,
  смерть и продвижение после уборки. Урон и HP печатаются из события без пересчёта.
- Показ обоих строёв после каждого полного хода и вывод победителя.
- Состояния `Setup → Recruitment → Battle → Result`; новая партия возвращает в `Setup`.
- Проверка чисел, повторный ввод при ошибке, корректный выход при конце ввода.
- UTF-8 для консоли Windows.

Пошаговый режим, ручная закупка, сохранения и кооператив не входят в этот MVP
согласно разделу 01 проектной документации.

## Текущее состояние ядра

В `main` пока подключены `tests/stubs/UnitStub.cpp`, `ArmyStub.cpp` и `EngineStub.cpp`.
Оболочка вызывает существующий движок, но этот движок ещё не реализует правила
боя и возвращает пустой список событий. Обычный запуск показывает изменения HP,
строи после уборки и итог; строки ударов появятся после интеграции ядра Ксюши.

`--demo-log` печатает заранее заданный список событий и явно помечен как
демонстрация. Это проверка рендера, а не симуляция по характеристикам каталога.
Подключение событий настоящего ядра не требует изменения форматтера.
После интеграции ядра из основного CMake нужно убрать его три заглушки,
как уже указано в комментарии интегратора.

## Сборка и запуск

Команды выполняются из корня репозитория. Для Windows/MSVC используйте
Developer Command Prompt / Developer PowerShell от Visual Studio с компонентом C++:

```text
cmake -S . -B build/ui-app -G Ninja -DCMAKE_BUILD_TYPE=Debug "-DCMAKE_CXX_FLAGS=/utf-8 /EHsc"
cmake --build build/ui-app
.\build\ui-app\shieldwall.exe
.\build\ui-app\shieldwall.exe --demo-log
```

`/utf-8` нужен и для русских строк интерфейса, и для уже существующих имён в
генераторе армий. `/EHsc` сохраняет обработку C++-исключений при явном задании
`CMAKE_CXX_FLAGS`. Основной `CMakeLists.txt` изменён только добавлением четырёх
файлов в конец списка исходников, как требуют правила команды.

Linux/macOS с компилятором C++17:

```text
cmake -S . -B build
cmake --build build
./build/shieldwall
./build/shieldwall --demo-log
```

Пример ввода: `40`, затем `42`, затем `1` — армии по 40 монет, seed 42 и автобой.
После результата `0` завершает программу, `1` начинает новую партию.
Для воспроизведения повторите seed, бюджет и действия меню, включая количество
повторных генераций. Повторная генерация продолжает поток случайных чисел.

Необязательный позиционный аргумент — путь к каталогу юнитов.
По умолчанию читается `data/units.txt` относительно текущей папки.

## Проверки

```text
cmake -S tests/ui -B build/ui-tests -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build/ui-tests
ctest --test-dir build/ui-tests --output-on-failure
```

Тестовая сборка сама включает `/utf-8` для MSVC. На Linux/macOS можно убрать
`-G Ninja`, если Ninja не установлен.

`ui_tests` проверяет события, варианты текста, неизменность переданных урона и HP,
повторяемость вывода, ошибки и границы числового ввода, EOF в меню, отмену до боя,
повторную генерацию, новую партию, завершение автобоя и совпадение состояния
армий с прямым `runToEnd()`. `data_tests` запускает существующие тесты Никиты
без изменения его файлов. Тесты используют готовые реализации ядра, а пока они
отсутствуют — те же заглушки, что используются в основной сборке.

## Вопрос интеграции для ревью

В документе указано выбирать фразы тем же экземпляром `mt19937`, что использует
бой, но в согласованном `BattleEngine.h` генератор закрыт, а конструктор принимает
только seed. Общие заголовки по правилам команды не изменены.

В этой ветке форматтер получает `mt19937&`, а меню создаёт отдельный генератор
текста с тем же seed. Так вывод воспроизводим и печать не влияет на исход боя.
Это явное отклонение от требования об общем экземпляре; решение требуется
согласовать с Ксюшей на ревью. Если команда решит открыть общий генератор,
правку общего заголовка нужно оформить отдельно согласно правилам проекта.

Для трактовки событий используются соглашения: `team=0` — Синие, `team=1` —
Красные; `actor` принадлежит `team`, в `Death` это погибший, в `Promote` —
вышедший вперёд. В `BattleEnd` команда обозначает победителя. Итог интерфейс
также получает из `BattleEngine::winner()`. Эти соглашения нужно подтвердить
при интеграции событий ядра.
